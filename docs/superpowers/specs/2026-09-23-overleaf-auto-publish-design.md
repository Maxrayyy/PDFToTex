# Overleaf 自动发布设计

## 目标

批次在服务器完成并正式发布 TEX 后，将整个批次目录自动同步到既有
Overleaf Cloud 项目。当前只启用仍有待处理任务的 U1 和 U3，不经过 GitHub；
U2 已全部完成，不进入自动发布扫描。

## 目录映射

| 分类 | 本地发布根目录 | Overleaf 项目内目标目录 |
| --- | --- | --- |
| U1 | `data/optimized/U1/批次数据` | `待审核/<批次号>` |
| U3 | `data/optimized/U3/20260808` | `U3_tex—待审核/20260808/<批次号>` |

每次同步只替换当前批次目录。项目中的其他批次、根目录文件和 Overleaf
产生的内容不受影响。

## 发布门槛

自动扫描器只处理启用时间之后完成的队列。队列必须满足以下条件：

- 状态文件中的所有任务均为 `done`，且退出码均为 `0`；
- 每个任务的 `output_tex` 均位于配置的分类发布根目录；
- 批次目录中至少存在一份 `.tex` 文件；
- 批次目录不包含符号链接；
- 同一队列中的输出可以明确归属于一个或多个批次目录。

手工发布命令使用相同的路径和文件校验，但不依赖队列状态，供补传和
故障恢复使用。

## Git 工作流

每个启用的 Overleaf 项目在服务器 `/srv/pdftotex/overleaf/projects/<unit>` 保留
独立工作树。发布时获取项目锁，拉取远端最新提交，将允许上传的文件同步到
目标批次目录，然后提交并推送。运行时文件、日志、SQLite、环境文件和缓存
目录沿用现有打包工具的排除规则。

推送成功后才向 JSONL 发布账本写入批次、内容 SHA-256、Overleaf commit、
队列状态文件和时间。内容哈希未变化时不产生空提交。失败不会写成功记录，
后续定时扫描会重试。

## 凭据

两个 remote URL 可以保存在服务器配置中，因为 URL 本身不含秘密。Git
authentication token 只写入 `pdftotex` 用户可读、权限 `0600` 的凭据文件，
不进入仓库、systemd unit、日志、进程参数或 remote URL。

Overleaf 专用 Git HOME 强制 HTTP/1.1；服务器存在本机 Mihomo 时，仅该 Git
HOME 配置 `http://127.0.0.1:7890` 代理，避免跨境大项目 clone 的 HTTP/2
中断，不修改系统或主仓库 Git 配置。

## 调度

systemd timer 每两分钟运行一次扫描器。配置中的 `enabled_after` 在安装时
生成，避免首次启动上传所有历史产物。发布器使用文件锁，定时任务重叠时只有
一个实例执行。

## 故障处理

- 远端有新提交：先拉取并重放本次本地提交，再推送；冲突时退出并保留日志。
- 网络或认证失败：本次返回失败，账本不记成功，下次定时任务重试。
- 批次内容后续人工修改：目录哈希变化后会生成新提交并更新同一目标目录。
- 删除本地批次：不会删除 Overleaf 上已发布目录。
